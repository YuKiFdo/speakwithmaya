# Live-session load test — OVH VPS, 2026-11-18

## Setup
- Target: OVH VPS (2 shared vCPU, Intel Haswell under KVM, 3.7 GB RAM), Ubuntu 26.04, Docker.
- Isolated container `maya-backend-loadtest` on :3100, same image as production, with
  `LIVE_FAKE_UPSTREAM=1` (fake Gemini Live: real-time 24 kHz audio replies, no API cost) and
  no production env (DB/storage pointed at a dead address). Production kept serving users.
- Generator (`maya-backend/scripts/loadtest/live-load.mjs`, run off-box via SSH tunnel) mimics
  the web client: binary 16 kHz mic frames, gated mic (Profile B), `turn_complete`, pings.
- Steps of N simultaneous sessions, 3 min each; aborts if production `/v1/health` fails or
  is slower than 3 s twice. Metrics: `vps-monitor.sh` (docker stats + vmstat every 2 s) and
  in-process CPU profiles via the inspector.

## Results

### Run 1 — before fixes (`87a108d`)
| Sessions | First AI audio p95 | Audio frame gap p99 / max | Test container CPU | Notes |
|---|---|---|---|---|
| 1 | 1.95 s | 242 ms / 2.5 s | ~55% | stalls with a single user |
| 5 | 1.81 s | 388 ms / 1.8 s | 68% avg, 103% peak | |
| 10 | 5.72 s | 569 ms / **8.7 s** | 80% avg, 123% peak | unusable; stopped here |

After all sessions closed: JS heap 57 MiB but process RSS ~660 MiB (native memory not returned).

### Profiling findings → fixes (`65f15e4`)
1. Nest `WsAdapter` ran `JSON.parse(data.toString())` on every WebSocket frame, including
   the 10/s binary mic frames per session (throwing each time), although no
   `@SubscribeMessage` handlers exist. → parser disabled.
2. Downlink audio sent as 50 JSON+base64 messages/s per session. → clients advertising
   `supportsOpusBatch` get 3 packets per message (~17/s); legacy clients unchanged.
3. RSS growth from glibc malloc arenas. → `MALLOC_ARENA_MAX=2` in the image.
4. Test artifact (container calling its own port as "Supabase", ~7% CPU) removed.

### Run 2 — after fixes (`65f15e4`)
| Sessions | First AI audio p95 | Test container CPU | Notes |
|---|---|---|---|
| 1 | 4.01 s | **31% avg** (was ~55%) | RSS 87 MiB (was 106 MiB) |
| 5 | 1.97 s | — | aborted mid-step by the production health guard |

Frame-gap numbers are not comparable between runs (messages now carry 60 ms of audio).

## Root cause of the remaining multi-second freezes: shared-CPU steal
- Host CPU **steal averaged 5–8% and peaked at 42–53%** in both runs: the hypervisor
  periodically took about half of the VPS's CPU.
- A profile with 3 active sessions was **91% idle**, yet event-loop delay still hit 2–2.7 s:
  time lost outside the process, not in our code.
- During the tests the host load average reached 3.8 on 2 vCPUs and production's own event
  loop saw 1–4 s spikes, which tripped the guard.

## Conclusions
1. The code fixes roughly halved per-session CPU and removed the memory growth.
2. **This VPS cannot reliably serve ~5+ simultaneous voice sessions**: not because of RAM
   (plenty free) or our per-session cost, but because its shared vCPUs are throttled by the
   host, producing multi-second audio freezes.
3. More shared cores would not fix steal. The fix is a VPS with **dedicated (non-shared) CPU
   cores**; then re-run this test to get the real capacity number.
4. Remaining code work (worth doing regardless): move end-of-session audio work (concat,
   resample, WAV encoding, uploads) off the main thread, so many sessions ending together
   cannot freeze live calls.

## Re-running
```
# on the VPS
cd ~/apps/maya-loadtest
docker compose -f docker-compose.loadtest.yml up -d && nohup bash vps-monitor.sh m.csv &
# from a workstation
ssh -N -L 3100:127.0.0.1:3100 ubuntu@<vps> &
node maya-backend/scripts/loadtest/live-load.mjs --url ws://localhost:3100/live-session \
  --steps 1,5,10,20 --hold 180 --guard https://api.speakwithmaya.com/v1/health
# afterwards
docker compose -f docker-compose.loadtest.yml down
```
